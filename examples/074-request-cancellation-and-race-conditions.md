# Request Cancellation, Stale Responses, and Race Conditions — Example

This Vite demo makes response-order bugs visible with three search panels:

1. **No protection:** every response updates the panel, so a slower old query can overwrite a newer result.
2. **Ignore obsolete results:** cleanup prevents old requests from updating the panel, but the requests continue.
3. **Abort and ignore:** cleanup aborts the supported work and also guards state updates.

All panels use the same local JSON file. The demo adds a query-dependent delay before reading its response body so requests can finish out of order consistently. This artificial delay is only for learning; it is not a network-performance measurement.

## `src/searchPeople.js`

The function fetches the local file, checks for HTTP failure, waits for a query-dependent demo delay, then reads and filters the JSON. The signal can abort both the fetch and the delay:

~~~js
function waitForDemoDelay(milliseconds, signal) {
  if (!signal) {
    return new Promise((resolve) => {
      setTimeout(resolve, milliseconds);
    });
  }

  return new Promise((resolve, reject) => {
    if (signal.aborted) {
      reject(signal.reason || new DOMException("Request aborted", "AbortError"));
      return;
    }

    const timeoutId = setTimeout(() => {
      signal.removeEventListener("abort", handleAbort);
      resolve();
    }, milliseconds);

    function handleAbort() {
      clearTimeout(timeoutId);
      signal.removeEventListener("abort", handleAbort);
      reject(signal.reason || new DOMException("Request aborted", "AbortError"));
    }

    signal.addEventListener("abort", handleAbort, { once: true });
  });
}

export async function searchPeople(query, signal) {
  const response = await fetch("/people.json", { signal });

  if (!response.ok) {
    throw new Error("Could not load people: HTTP " + response.status);
  }

  const normalizedQuery = query.trim().toLowerCase();

  // Demo only: short queries take longer so responses can finish out of order.
  const demoDelay =
    normalizedQuery.length === 0
      ? 120
      : Math.max(180, 1250 - normalizedQuery.length * 190);

  await waitForDemoDelay(demoDelay, signal);

  // The body is read after the delay so aborting can also stop body consumption.
  const people = await response.json();

  if (!normalizedQuery) {
    return people;
  }

  return people.filter((person) => {
    const searchableText = person.name + " " + person.role;
    return searchableText.toLowerCase().includes(normalizedQuery);
  });
}
~~~

When the query gets longer, its artificial delay gets shorter. Type a short query such as `a` and then quickly extend it to `asha`. The newer request can finish first; without protection, the older result may then overwrite it.

## `src/App.jsx`

~~~jsx
import { useEffect, useState } from "react";
import { searchPeople } from "./searchPeople.js";

const strategies = {
  unsafe: {
    title: "No protection",
    description:
      "Every completion updates state. An older, slower response can overwrite the latest query.",
  },
  ignore: {
    title: "Ignore obsolete results",
    description:
      "Cleanup blocks stale state updates. The old request still runs to completion.",
  },
  abort: {
    title: "Abort and ignore",
    description:
      "Cleanup aborts supported work and guards state updates for the old query.",
  },
};

function PeopleList({ people }) {
  if (people.length === 0) {
    return <p className="empty">No people match that query.</p>;
  }

  return (
    <ul className="people">
      {people.map((person) => (
        <li className="person" key={person.id}>
          <strong>{person.name}</strong>
          <span>{person.role}</span>
        </li>
      ))}
    </ul>
  );
}

function SearchPanel({ strategy, query }) {
  const [result, setResult] = useState({
    status: "loading",
    query,
    people: [],
    error: null,
  });

  useEffect(() => {
    let ignore = false;
    const controller =
      strategy === "abort" ? new AbortController() : null;
    const signal = controller ? controller.signal : undefined;

    setResult({ status: "loading", query, people: [], error: null });

    searchPeople(query, signal)
      .then((people) => {
        if (strategy === "unsafe" || !ignore) {
          setResult({ status: "success", query, people, error: null });
        }
      })
      .catch((error) => {
        if (signal?.aborted) {
          return;
        }

        if (strategy === "unsafe" || !ignore) {
          setResult({ status: "error", query, people: [], error });
        }
      });

    return () => {
      if (strategy !== "unsafe") {
        ignore = true;
      }

      controller?.abort();
    };
  }, [query, strategy]);

  const config = strategies[strategy];
  const isStale = result.query !== query;

  return (
    <section className={"panel panel-" + strategy}>
      <h2>{config.title}</h2>
      <p className="description">{config.description}</p>

      {result.status === "loading" && (
        <p className="loading" role="status">
          Loading response for “{result.query || "all people"}”…
        </p>
      )}

      {result.status === "error" && (
        <div className="error" role="alert">
          <p>
            Request for “{result.query || "all people"}” failed:{" "}
            {result.error.message}
          </p>
        </div>
      )}

      {result.status === "success" && (
        <>
          <p className={isStale ? "response stale" : "response"} role="status">
            Response for “{result.query || "all people"}”
            {isStale && (
              <strong>
                {" "}
                — stale; current input is “{query || "all people"}”
              </strong>
            )}
          </p>
          <PeopleList people={result.people} />
        </>
      )}
    </section>
  );
}

export default function App() {
  const [query, setQuery] = useState("");

  return (
    <main className="app">
      <p className="eyebrow">React Effect cleanup</p>
      <h1>Request races</h1>
      <p className="intro">
        Type quickly and compare what happens when older responses finish after
        newer ones. The dataset is local; no external API is contacted.
      </p>

      <label className="search">
        <span>Search people</span>
        <input
          type="search"
          value={query}
          onChange={(event) => setQuery(event.target.value)}
          placeholder="Type a, then quickly add sha"
        />
      </label>

      <div className="panels">
        <SearchPanel strategy="unsafe" query={query} />
        <SearchPanel strategy="ignore" query={query} />
        <SearchPanel strategy="abort" query={query} />
      </div>

      <aside className="explanation">
        <h2>What to notice</h2>
        <ul>
          <li>
            The unprotected panel may show a response whose query differs from
            the input.
          </li>
          <li>
            The ignore panel avoids stale updates, but it does not cancel old
            work.
          </li>
          <li>
            The abort panel passes a signal to fetch and to the simulated delay,
            and ignores obsolete state updates.
          </li>
        </ul>
        <p>
          Aborting a browser request does not guarantee that a server never
          received it or stopped processing it. This demo's delay is local
          simulation, not server-side cancellation.
        </p>
      </aside>
    </main>
  );
}
~~~

The **No protection** panel intentionally omits a relevance guard. The other two use an Effect-local `ignore` flag. The **Abort and ignore** panel also passes a fresh controller signal to its request.

Each panel has its own Effect and request. This keeps the strategies independent so their behavior can be compared directly.

## Run and explore

Start the Vite development server:

~~~sh
npm run dev
~~~

Try this sequence:

1. Wait for the initial list to load.
2. Type `a`, then quickly type `asha`.
3. Compare the query shown above each result list with the current input.
4. The unprotected panel can show the slower old response last.
5. The ignore panel keeps obsolete responses from changing state, but those requests still finish.
6. The abort panel cleans up the old request and ignores its result. In the Network panel, inspect requests and cancellations.
7. Block `/people.json` in developer tools to see the real error state, then remove the block and reload.

The local file is small, so the artificial delay creates the visible race. It only simulates variable completion time; it does not represent how a real API server handles an aborted request.

## Common mistakes

- Assuming the first request will finish first.
- Guarding success but forgetting to guard the error update.
- Thinking the ignore flag cancels the request.
- Treating abort as proof the server never received or processed a request.
- Reusing a controller after it has been aborted.
- Showing a result for an old query without identifying it as stale.
- Assuming aborting also debounces future keystrokes.
- Treating Strict Mode's development-only setup/cleanup check as a production duplicate-request bug.

## Key takeaway

Cancellation and stale-result protection have separate jobs. Abort supported work that is no longer needed, and only let a result update state while it still belongs to the current request. Keep the query that produced each result so the UI can never mistake stale data for current data.
