# React DOM Roots, Hydration, and Client APIs - Example

This example compares the two client entry APIs:

- `index.html` starts with an empty root and uses `createRoot`.
- `hydrated.html` starts with matching markup already in the root and uses `hydrateRoot`.

The hydration page contains a hand-written HTML fixture whose initial structure and text match `HydratedApp` in `src/App.jsx`. It demonstrates the client hydration call, but it is not a server-rendering implementation. In a real server-rendered application, the server or framework generates HTML from the same React component and initial data.

## Start a React project

Create a React project using Vite, then enter the project and install its dependencies:

~~~sh
npm create vite@latest react-dom-roots-demo -- --template react
cd react-dom-roots-demo
npm install
~~~

Replace or add the files below. Keep the project setup files generated by Vite.

## `index.html`: empty client root

Use an empty container for the client-rendered page:

~~~html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Client root example</title>
  </head>
  <body>
    <div id="root"></div>
    <script type="module" src="/src/main.jsx"></script>
  </body>
</html>
~~~

## `hydrated.html`: existing matching markup

This page starts with HTML already in the root. Its initial markup must match the first output of `HydratedApp` in `src/App.jsx`. Keep this fixture compact so it does not introduce extra text whitespace between the rendered elements.

~~~html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Hydration example</title>
  </head>
  <body>
    <div id="root"><main class="card"><h1>Server-rendered interface</h1><p>This HTML is visible before the client JavaScript runs.</p><button type="button">Activate hydrated button</button></main></div>
    <script type="module" src="/src/hydrate.jsx"></script>
  </body>
</html>
~~~

In a real app, a server-rendering API or framework would produce the HTML inside `#root` from the same component. This static fixture lets you see what `hydrateRoot` expects without adding a server to the demo.

## `src/App.jsx`: two small interfaces

~~~jsx
import { useState } from "react";
import "./styles.css";

export function ClientApp() {
  const [count, setCount] = useState(0);

  return (
    <main className="card">
      <p className="eyebrow">createRoot</p>
      <h1>Client-rendered interface</h1>
      <p>This page began with an empty root container.</p>
      <button
        type="button"
        onClick={() => setCount((current) => current + 1)}
      >
        Client clicks: {count}
      </button>
    </main>
  );
}

export function HydratedApp() {
  const [clicks, setClicks] = useState(0);

  return (
    <main className="card">
      <h1>Server-rendered interface</h1>
      <p>This HTML is visible before the client JavaScript runs.</p>
      <button
        type="button"
        onClick={() => setClicks((current) => current + 1)}
      >
        {clicks === 0
          ? "Activate hydrated button"
          : "Hydrated clicks: " + clicks}
      </button>
    </main>
  );
}
~~~

`HydratedApp` must initially render the same `main`, heading, paragraph, and button text as the HTML fixture. The state-backed label changes only after a click, once React has attached the event handler.

## `src/main.jsx`: create a client root

~~~jsx
import { createRoot } from "react-dom/client";
import { ClientApp } from "./App.jsx";

const container = document.getElementById("root");

if (!container) {
  throw new Error("The #root container was not found.");
}

createRoot(container).render(<ClientApp />);
~~~

This page has no pre-rendered React interface inside `#root`, so `createRoot` is the correct API. Its first render creates the content in that container.

## `src/hydrate.jsx`: adopt existing markup

~~~jsx
import { hydrateRoot } from "react-dom/client";
import { HydratedApp } from "./App.jsx";

const container = document.getElementById("root");

if (!container) {
  throw new Error("The server-rendered #root container was not found.");
}

hydrateRoot(container, <HydratedApp />);
~~~

This page already contains the initial `HydratedApp` markup, so it uses `hydrateRoot`. React reuses the matching elements and attaches the button's click behavior. Do not replace this call with `createRoot`: doing so would clear the fixture and perform a client render instead.

## Run and compare

Start Vite:

~~~sh
npm run dev
~~~

Open the default page to see the client root. Then open `hydrated.html` on the same development server to see the hydration fixture.

On the first page, the interface appears after the client entry runs. On the hydration page, the fixture's HTML is present before `hydrate.jsx` executes; after hydration, clicking the button updates its label. Both pages respond to clicks, but their starting container contents and root APIs are different.

## Common mistakes to check

- The root lookup returns `null` because the element ID is missing or misspelled.
- `createRoot` is used for `hydrated.html`, which clears the pre-existing fixture.
- `hydrateRoot` is used for `index.html`, which has no markup to hydrate.
- The heading, paragraph, attributes, or initial button text in the fixture differs from `HydratedApp`.
- A developer adds a browser-only condition to `HydratedApp` so its first client render no longer matches the fixture.
- Extra text or whitespace is inserted between the fixture's elements.
- The example is described as server-side rendering even though `hydrated.html` is a hand-authored stand-in.

## Key takeaway

Choose the root API from the initial contents of the container: `createRoot` for an empty client-rendered container and `hydrateRoot` for matching React HTML already rendered into the page. Keep the first hydrated output identical, then let React state handle interaction.
