# Client-Side Data Fetching, the `use` API, and Async Values - Example

This Vite demo shows two client-side ways to load the same local people list:

1. **Effect and state:** fetch the file after the component commits, and render explicit loading, error, and result states.
2. **Promise and Suspense:** read a cached Promise with React's `use` API, show a Suspense fallback while it is pending, and let an Error Boundary handle a rejection.

The small Promise map is included to make Promise identity visible. It is a teaching example, not a production data cache. For a real application, use the framework or Suspense-compatible data library you have selected.

This example uses React 19 or newer because it uses `use` with a Promise.

## `src/people.js`

Both approaches call `loadPeople`. The Effect approach supplies an `AbortSignal`. The Suspense approach calls `getPeoplePromise`, which returns the same Promise for a normalized query:

~~~js
const peoplePromises = new Map();

function normalizeQuery(query) {
  return query.trim().toLowerCase();
}

function filterPeople(people, query) {
  const normalizedQuery = normalizeQuery(query);

  if (!normalizedQuery) {
    return people;
  }

  return people.filter((person) => {
    const searchableText = person.name + " " + person.role;
    return searchableText.toLowerCase().includes(normalizedQuery);
  });
}

export async function loadPeople(query, signal) {
  const response = await fetch("/people.json", { signal });

  if (!response.ok) {
    throw new Error("Could not load people: HTTP " + response.status);
  }

  const people = await response.json();
  return filterPeople(people, query);
}

export function getPeoplePromise(query) {
  const key = normalizeQuery(query);

  if (!peoplePromises.has(key)) {
    const promise = loadPeople(key).catch((error) => {
      // Do not keep a rejected Promise; retry should be able to try again.
      peoplePromises.delete(key);
      throw error;
    });

    peoplePromises.set(key, promise);
  }

  return peoplePromises.get(key);
}

export function forgetPeoplePromise(query) {
  peoplePromises.delete(normalizeQuery(query));
}
~~~

This example's cache holds one Promise for each query for as long as the page is open. It has no expiry or size limit. A production cache needs an intentional lifetime, invalidation rules, and any required user or permission scoping.

## `src/ErrorBoundary.jsx`

A rejected Promise read with `use` is sent to an Error Boundary. React does not provide a built-in function component for declaring one, so this small class component is used in the demo:

~~~jsx
import { Component } from "react";

export default class ErrorBoundary extends Component {
  state = { error: null };

  static getDerivedStateFromError(error) {
    return { error };
  }

  handleRetry = () => {
    this.props.onRetry?.();
    this.setState({ error: null });
  };

  render() {
    if (this.state.error) {
      return (
        <div className="error" role="alert">
          <p>Could not load this list: {this.state.error.message}</p>
          <button type="button" onClick={this.handleRetry}>
            Try again
          </button>
        </div>
      );
    }

    return this.props.children;
  }
}
~~~

The retry callback clears the failed Promise from the map before the boundary renders its children again. The next read can therefore create a new request.

## `src/App.jsx`

The first panel stores request status and results in state. Its Effect aborts the previous request when the query changes or the component unmounts.

The second panel reads a cached Promise. A pending read is handled by `<Suspense>`; a rejected read is handled by `ErrorBoundary`:

~~~jsx
import { Suspense, use, useEffect, useState } from "react";
import ErrorBoundary from "./ErrorBoundary.jsx";
import {
  forgetPeoplePromise,
  getPeoplePromise,
  loadPeople,
} from "./people.js";

function PeopleList({ people }) {
  if (people.length === 0) {
    return <p className="empty">No people match this search.</p>;
  }

  return (
    <ul className="people">
      {people.map((person) => (
        <li className="person" key={person.id}>
          <strong>{person.name}</strong>
          <span>{person.role}</span>
        </li>
      ))}
    </ul>
  );
}

function EffectPeoplePanel({ query }) {
  const [result, setResult] = useState({
    query: null,
    status: "loading",
    people: [],
    error: null,
  });

  useEffect(() => {
    const controller = new AbortController();

    setResult({ query, status: "loading", people: [], error: null });

    loadPeople(query, controller.signal)
      .then((people) => {
        setResult({ query, status: "success", people, error: null });
      })
      .catch((error) => {
        if (controller.signal.aborted) {
          return;
        }

        setResult({ query, status: "error", people: [], error });
      });

    return () => controller.abort();
  }, [query]);

  // Before the Effect for a new query runs, do not show the prior query's data.
  const currentResult =
    result.query === query
      ? result
      : { status: "loading", people: [], error: null };

  if (currentResult.status === "loading") {
    return <p className="loading" role="status">Loading with an Effect…</p>;
  }

  if (currentResult.status === "error") {
    return (
      <p className="error" role="alert">
        Could not load this list: {currentResult.error.message}
      </p>
    );
  }

  return <PeopleList people={currentResult.people} />;
}

function SuspensePeoplePanel({ query }) {
  const people = use(getPeoplePromise(query));
  return <PeopleList people={people} />;
}

function Panel({ title, description, children }) {
  return (
    <section className="panel">
      <h2>{title}</h2>
      <p className="description">{description}</p>
      {children}
    </section>
  );
}

export default function App() {
  const [query, setQuery] = useState("");

  return (
    <main className="app">
      <p className="eyebrow">React async data</p>
      <h1>Two client-side loading patterns</h1>
      <p className="intro">
        Search the same local list in both panels. The requests are independent
        so you can compare each panel's loading behavior.
      </p>

      <label className="search">
        <span>Filter people</span>
        <input
          type="search"
          value={query}
          onChange={(event) => setQuery(event.target.value)}
          placeholder="Try “design” or “Asha”"
        />
      </label>

      <div className="panels">
        <Panel
          title="Effect and state"
          description="The component starts a request after commit and renders status from state."
        >
          <EffectPeoplePanel query={query} />
        </Panel>

        <Panel
          title="Promise and Suspense"
          description="The component reads a cached Promise; boundaries handle pending and rejected states."
        >
          <ErrorBoundary onRetry={() => forgetPeoplePromise(query)}>
            <Suspense
              fallback={
                <p className="loading" role="status">
                  Loading with Suspense…
                </p>
              }
            >
              <SuspensePeoplePanel query={query} />
            </Suspense>
          </ErrorBoundary>
        </Panel>
      </div>

      <p className="note">
        The Promise map is intentionally small and is not a production cache.
        The Effect panel also aborts a request when its query changes.
      </p>
    </main>
  );
}
~~~

The `EffectPeoplePanel` stores which query produced its current result. When the input changes, it displays loading instead of briefly showing results for the previous query before the new Effect runs.

The `SuspensePeoplePanel` does not create a Promise inline. Its data source returns a cached Promise for the normalized query. When that Promise is pending, the nearest Suspense boundary shows its fallback.

## Run and explore

Start the development server:

~~~sh
npm run dev
~~~

Try these steps:

1. Search for a name such as **Asha**. Both panels filter the same local list.
2. Search for **design** to match roles as well as names.
3. Clear the search to show all people.
4. Watch the Effect panel's loading text and the Suspense panel's fallback. The local file is small, so either loading state may appear only briefly.
5. In developer tools, block the `people.json` request or rename the local file to observe the two error paths. Restore the file afterward. The Suspense panel's **Try again** button clears the rejected Promise from the demo cache.

The demo uses a static local file and filters the returned array in the browser. A real application would usually request the relevant query from an API, apply an intentional cache policy, and use the framework's recommended data-loading approach.

## Common mistakes

- Creating a new Promise inside `SuspensePeoplePanel` on every render instead of reading from the stable resource.
- Expecting the Effect request to show the Suspense fallback.
- Forgetting to inspect `response.ok` before parsing JSON.
- Leaving rejected Promises in the cache so retry repeats the same rejection.
- Assuming this small map provides cache expiry, invalidation, size limits, or account isolation.
- Forgetting that each search query starts separate requests in this demo.
- Treating the short-lived fallback as proof of a performance improvement.

## Key takeaway

The Effect panel owns request status in state and cleans up obsolete work. The Suspense panel reads a stable cached Promise, while Suspense and an Error Boundary handle pending and rejected outcomes. Pick the loading model supported by the app's framework or data layer, and give that system clear ownership of each request.
